# Быстрый подбор: сбор одним проходом клиента

## Использование

1. Включить **«Разное → Быстрый подбор»**.
2. Открыть контейнер обычным способом.
3. Нажать штатную кнопку сбора всех предметов.

Отдельная кнопка оверлея не добавляется. Настройка сама не начинает сбор, не открывает контейнеры и не переносит предметы на расстоянии. По умолчанию выключена, сохраняется в профиле. «Сброс» под FOV/руками её не меняет.

### Что исправлено после варианта с нулевым таймером

- Тумблер менял `fast_loot`, но его анимация `a_fast_loot` не обновлялась. Добавлен пропущенный `Tick` в кадровый цикл меню. Теперь визуальное положение следует тому же bool, что используется контроллером, в том числе после загрузки профиля.
- `WaitForSeconds(0)` всё равно создавал асинхронное ожидание. Поэтому обнуление аргумента не превращало сбор в один проход.
- Теперь пропускается **весь блок межпредметного ожидания и await**, а не только заданная длительность. После обычного запроса переноса цикл сразу переходит к следующему слоту. Все подходящие слоты обрабатываются в одном синхронном проходе клиента, в штатном обратном порядке.

**Это не атомарное серверное «забрать всё».** На каждый предмет по-прежнему отправляется штатная команда. Сервер проверяет место, права, состояние контейнера и может ограничивать/отклонять запросы. Подтверждение и обновление интерфейса зависят от сети и сервера. Мгновенное зачисление всего содержимого, независимо от этих условий, не заявляется. Принятые сервером предметы нужно проверять после повторного открытия контейнера.

## Границы изменений

Не меняются item count, сетевые ID, копии инвентаря, серверные права, обычные команды переноса и проверки перед ними. Штатный контроллер сбора общий для нескольких видов контейнеров. Обратная операция «загрузить всё в контейнер» (`FastLoadAll`) не изменяется.

Синхронный проход идёт от последнего индекса к нулю, не добавляет повторных попыток и не повторяет уже просмотренный слот. Проверки живого источника, состояния окна/инвентаря и содержимого слота выполняются на каждой итерации. Завершение и очистка флага сбора остаются штатными.

**Отмена:** проверка cancellation token, которая находилась внутри пропущенного ожидания, больше не выполняется между командами. UI не может обработать закрытие окна или выключение тумблера посреди одного синхронного callback: событие обработается после прохода. Выключение возвращает обычный алгоритм для следующих проходов, но не отзывает уже отправленные запросы. Очень большие контейнеры могут вызвать краткую нагрузку на главный поток; на устройстве это ещё нужно проверить.

## Подтверждение по исходным образам

В `LootScreenViewImpl` есть `collectButton` (+0x48) и отдельный `fastLoadButton` (+0x50). `LootScreenPresenter` получает `xg collectLootController`; реализация — `xw` (релиз) / `vB` (бета).

| | Релиз | Бета |
|---|---:|---:|
| libil2cpp GNU build ID | `d85e63cd8dcbd481695012ef2e284f0eeb9ef307` | `e10795349bd7c2cdc7d8527597c64395a4efed79` |
| `CollectAllItems.MoveNext` RVA | `0x5B5C5BC` | `0x5AF47EC` |
| Изменяемая инструкция RVA | `0x5B5CAD4` | `0x5AF4D04` |
| Цель перехода: следующий индекс | `0x5B5CC48` | `0x5AF4E78` |
| Возврат к проверке следующего слота | `0x5B5C914` | `0x5AF4B44` |

Меняется одна выровненная 4-байтовая инструкция: прежняя загрузка длительности `LDR S0,[X8,...]` заменяется на `B PC+0x174` (`0x1400005D`). Переход находится **после** вызова переноса текущего предмета и попадает на штатный хвост:

```asm
LDR W8, [X19, #0x38]   // sourceIndex
SUB W8, W8, #1
STR W8, [X19, #0x38]
TBZ W8, #31, loop      // продолжить, пока индекс неотрицательный
```

Обходит `WaitForSeconds`, подготовку awaiter, проверку завершения и постановку продолжения в PlayerLoop. Не перескакивает через отправку команды или через проверки следующего слота. Никакие поля асинхронной машины вручную не фабрикуются. Используется базовая инструкция ARM64, FP16 не нужен. Общие float-константы и глобальный scheduler Unity не меняются.

## Контроль версии и восстановление

- До записи сверяются все 20 байт GNU build ID, 8 инструкций вокруг места изменения и 4 инструкции **в цели перехода**.
- Неизвестная версия, изменённый соседний код/хвост или чужой патч отклоняются без записи.
- Чужие патчи, включая оставшиеся от старого экземпляра варианты 0 / 1 мс / 0,125 с, не присваиваются и не перезаписываются.
- Запись — существующим `/proc/<pid>/mem`, одним выровненным словом; после записи читается результат. На стандартном Linux/Android arm64 kernel `copy_to_user_page` выполняет обслуживание кеша исполняемой страницы. Защиты страницы не меняются, альтернативные способы обхода отказа записи не добавляются.
- Проверка состояния — раз в 250 мс; переключение сразу. Повторной записи уже установленной инструкции каждый кадр нет.
- Выключение восстанавливает только свою инструкцию; неудачное восстановление повторяется на следующих тиках.
- На штатном выходе/смене сборки выполняется попытка восстановления. При потере процесса адрес забывается без записи. После принудительного убийства оверлея восстановление не гарантируется.

**При обновлении** штатно закрыть старый оверлей с восстановлением. Если он был убит принудительно, перезапустить игру перед запуском новой версии, чтобы в памяти не остался старый патч.

Настройка занимает бит 4 (`16`) flags существующего расширения VMW1 v1, 32 байта. Формат профиля не менялся.

## Проверки

```sh
sh tools/fast_loot/run.sh
python3 tools/fast_loot/check_native.py /path/to/release/libil2cpp.so /path/to/beta/libil2cpp.so
sh tools/viewmodel/run.sh
sh tools/lang/run.sh
sh tools/hostcheck/run.sh
```

Стенд вызывается из `build.sh` перед NDK-сборкой. Проверены обе версии, кодировка/цель перехода, отпечаток хвоста и отказ при его изменении, включение/выключение без потери оригинала, ошибки чтения/записи/readback и повтор восстановления, потеря сессии, конфликт со старыми патчами. Проверяется связь всех трёх misc-тумблеров с их кадровой анимацией. Отдельный процесс-ребёнок с RX-страницей подтверждает настоящую запись/восстановление через `/proc/pid/mem`.

Нативная проверка подтверждает переход к убывающему индексу и существующим проверкам следующего слота, а также пропуск await. Проверка границ прохода охватывает 0/1/12/30/60/96 слотов. Это не эмуляция полного сетевого клиента и не тест принятия команд сервером.

**На Android новый пакетный режим пока не проверен.** Пользователь подтвердил работу предыдущего патча, но сообщил, что таймерные версии всё равно собирали по одному. На устройстве проверить новый режим на нескольких стаках, пустом/полном инвентаре, ящиках/трупах, повторном открытии, отключении функции и нормальном выходе. Если часть предметов остаётся, нужен лог/наблюдение серверной реакции — подменой локальных чисел инвентаря это не исправляется.
