# RT-Dev драйвер — протокол

Источник: `rt dev Драйвера root cheat.zip`, каталог `RT【Dev】Driver`.
Архив содержит 23 загрузочных `.sh` для ядер 4.9–6.6. Каждый скрипт отделяет
ELF после маркера `#BY x Kitten x` и загружает его через `insmod /data/tmpf`.

## Подтверждённый ABI

Статически разобраны все 23 извлечённых ELF-модуля. У всех одинаковый публичный
протокол:

- module name: `RTkernel`;
- `init_module` регистрирует char-устройство и генерирует его имя случайно;
- `dispatch_ioctl` принимает `COPY_MEMOBY` размером `0x20`:
  `u32 pid` в `+0x00`, padding, `u64 addr` в `+0x08`, `u64 buffer` в `+0x10`,
  `u64 size` в `+0x18`;
- `OP_READ_MEM = 0x801`, `OP_WRITE_MEM = 0x802`,
  `OP_MODULE_BASE = 0x803`; enum также объявляет `OP_INIT_KEY = 0x800`.

Клиент использует только `0x801` и `0x802`. Базы библиотек получаются через
`/proc/<pid>/maps`, поэтому `0x803` не нужен. `read_process_memory` и
`write_process_memory` выполняют трансляцию одной страницы на запрос; транспорт
обязан разбивать запросы на куски, не пересекающие 4 КБ.

Проверка воспроизводима командой `python3 scripts/verify_rt_dev_archive.py`:
она извлекает ELF из каждого `.sh`, требует AArch64 char-device symbols,
проверяет машинные сравнения `cmd` с `0x801/0x802/0x803` и размер запроса
`0x20` в dispatch path.

## Клиент

`jni/src/kernel_io.h`: `RtDevTransport` сканирует `/dev` только на экране выбора
режима/перед привязкой, отбирает root-owned пустые char-устройства с коротким
именем из строчных букв и подтверждает кандидат чтением и записью собственной
памяти. После подтверждения fd живёт до завершения процесса; весь доступ к игре
проходит через `g_mem` и этот транспорт.

RT-Dev не является RT-Hook: тот использует перехваченный syscall `ioctl` с
командами `0x259/0x25a`, не создаёт `/dev`-узел и описан отдельно в
`reversing/NOTES_RT.md`. Оба транспорта выбираются разными кнопками.
