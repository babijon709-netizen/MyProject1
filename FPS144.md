# Лимиты FPS 90 / 120 / 144 и сброс

В «Разное → Лимит FPS» доступны кнопки **90 FPS / 120 FPS / 144 FPS** и **«Сброс»**. Выбранная кнопка подсвечивается. По умолчанию используется обычный игровой лимит; режим сохраняется в профиле. Сброс FOV/рук его не меняет.

Сброс FPS отменяет переопределение и возвращает сохранённое исходное значение игры — не принудительные 60 FPS. Переключения 90→120→144 не заменяют этот оригинал нашими промежуточными значениями.

Настройка FPS хранится в 32-байтовом VMW1 v2: биты flags 2..3 кодируют 0 — обычный режим, 1 — 144, 2 — 90, 3 — 120. Профили VMW1 v1 импортируются с сохранением FPS; их старые флаги подбора и патчей оружия отбрасываются. Бит 4 больше не используется. Новые биты оружия v2 описаны в [WEAPON_TUNING.md](WEAPON_TUNING.md). Неизвестные биты отвергаются; недопустимый fps_limit нормализуется в обычный режим.

## Что меняется

Устанавливается **игровой `UnityEngine.Application.targetFrameRate` на выбранные 90, 120 или 144** — backing int32 в `libunity.so` процесса игры. Частота цикла оверлея, touch и счётчики FPS не изменяются. Оригинал сохраняется; при сбросе, нормальном выходе и переключении версии выполняется условное восстановление. Если игра сама сменила graphics preset, его новое значение не затирается старым снимком.

Применение работает независимо от ESP и наличия локального игрока, раз в 100 мс; переключение режима и сброс обрабатываются без этой задержки. При отсутствии библиотеки повтор поиска — не чаще раза в секунду. Неоднозначные образы и неподдерживаемые версии отклоняются. После потери процесса старые адреса забываются без записи.

**Важно:** это поднятие целевого лимита Unity, а не гарантированные 144 отрисованных кадра. Экран, Android, энергосбережение, производительность и отдельный frame pacing могут ограничивать частоту ниже. На устройстве новая функция пока не проверена.

**Известное ограничение Swappy:** нативный setter Unity не только пишет int32, но также вызывает обновление Android frame pacing. Этот внешний memory-контроллер не выполняет код внутри игры и не вызывает JNI/Swappy setter. Если активен Swappy с ранее выбранным интервалом, одного обновления targetFrameRate может оказаться недостаточно для снятия его дополнительного лимита. Полный обход такого режима здесь не заявляется; нужно проверить реальный игровой FPS на устройстве. Успешная запись выбранного лимита в логах не считается измерением FPS.

## Подтверждённые native-адреса

Все RVA ниже относятся к **libunity.so**, не libil2cpp.so.

| | Релиз | Бета |
|---|---:|---:|
| GNU build ID | `7eb634edc8dede69` | `9417acde63f688ed` |
| Build ID RVA | `0x318` | `0x318` |
| Getter | `0x7390E0` | `0x7392F0` |
| Setter | `0x7390EC` | `0x7392FC` |
| Backing int32 | `0x17B8184` | `0x17B8A74` |

Путь релиза: строка `UnityEngine.Application::get_targetFrameRate` (RVA `0x1B6D24`) → регистрация icall на `0x5C9378` → thunk `0x5AB344` → getter. Setter регистрируется сразу следом (`0x5C938C` → `0x5AB348`). Getter выполняет ADRP/LDR W0/RET; соседний setter — ADRP/STR W0 и переход к обновлению pacing (`0x900608` → `0x8FCAC8`). Обычный расчёт частоты `0x7390F8` читает тот же int32, тогда как активный Swappy может подставлять свой интервал (`0x8FCA44`).

У беты регистрация setter — `0x5C9584` → `0x5AB4BC` → `0x7392FC`. Смещения не копировались из релиза вслепую.

Перед каждой серией записей/восстановлением проверяются точный build ID и три инструкции getter. Неизвестный движок остаётся без записей. Native layout хранится отдельно в `jni/src/fps_memory.h`, потому что managed offset generator не анализирует libunity.so.

## Проверки

```sh
sh tools/viewmodel/run.sh
# После распаковки исходных библиотек:
python3 tools/viewmodel/check_unity_fps.py /path/to/release/libunity.so /path/to/beta/libunity.so
```

Стенд проверяет оба build ID, неизвестную библиотеку, изменённый код, недопустимое исходное значение, независимость от FOV/рук, все режимы и переключения между ними без потери оригинала, сброс к исходным -1/30/60/90/120/144/300, preset 60→300, восстановление -1, ошибки чтения/записи и повтор восстановления, потерю сессии и конфиги с новым/старым flags. Он выполняется в `build.sh` перед NDK-сборкой.

На устройстве: выбрать максимальную частоту экрана, выключить энергосбережение, измерить именно игровой FPS для каждого режима и после сброса, проверить возврат прежнего лимита, меню/матч, сворачивание и смену graphics preset. Отдельно проверить устройство/режим с optimized frame pacing; не делать вывод по частоте оверлея.
