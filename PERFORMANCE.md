# Оптимизация оверлея: что и почему ускорено

Цель — убрать лаги, НЕ меняя того, что функции делают. Ни одна проверка не
ослаблена, ни один перебор не урезан: изменены только объём работы на кадр и
частота обращений к ядру.

## Откуда брались тормоза

Кадргист с устройства (`benzware_aim.log`, 1628 секунд наблюдения):

```
кадргист: 60/0/0/0/0 (<20/<34/<50/<100/>=100мс) ... чтений/кадр 8527
кадргист: ... худший 13667 220мс (esp 218 аим 0 фарм 0 меню 0 фри 0 своп 2)
кадргист: ... худший 12469 222мс (esp 5 аим 214 фарм 0 меню 0 фри 0 своп 3)
```

Два разных явления:

1. **Фон** — 8500 логических чтений памяти игры в каждом кадре.
2. **Всплески** — 98 кадров по 100–250 мс за 1628 секунд, почти все в стадии
   `esp` (35 % суммарного времени худших кадров, не считая свопа).

## 1. Кэш блоков памяти: кольцо из 8 → набор 64×4

`jni/src/mem_io.h`

Было: восемь блоков по 128 байт в одном кольце с вытеснением по кругу. ESP за
кадр обходит камеру, десяток игроков, их кости, маркеры и оружие — на таком
обходе девятый адрес выбивал первый, и кэш промахивался практически всегда.

Стало: 64 группы по 4 блока (256 блоков, 32 КБ на поток). Адрес всегда ищется
в своей группе по индексу — обход разных объектов больше не выбивает сам себя,
а поиск стоит четыре сравнения вместо линейного прохода.

Срок жизни данных не изменился: кэш живёт один кадр (`frame_begin`), запись в
блок по-прежнему помечает его некэшируемым.

Замер на стенде `tools/memio/run.sh`, перемежающийся обход (поле за полем у
всех объектов — ровно так ходит ESP):

| | syscall'ов | попаданий |
|---|---|---|
| было (кольцо из 8) | 3840 из 3840 | 0 |
| стало (64×4) | 320 из 3840 | 3520 |

**В 12 раз меньше обращений к ядру** на том же наборе чтений. Стенд падает на
старом кэше, так что регрессия сюда больше не вернётся.

Дополнительно: `written_recently()` вызывался на каждом попадании и делал
восемь атомарных чтений. Теперь при нулевом счётчике меток (обычное состояние:
метки ставят только Иксрей и «Всегда день») он выходит по одному чтению.

## 2. Перебор раскладок иерархии: бюджет на кадр

`jni/src/game.cpp` — `discover_layout_from_native_transforms()`

Это самая тяжёлая работа во всём чите: 3 сида × 61 смещение данных × 4
смещения индекса × 33 пары массивов × 4 варианта разыменования, и каждый
прочитавшийся кандидат ещё проверяется по всем известным трансформам с
подъёмом по родителям. Целиком — сотни миллисекунд в одном кадре, это и есть
«esp 218 мс» из кадргиста.

Перебор оставлен полным: тот же порядок обхода, тот же отбор лучшего, тот же
результат. Изменено одно — за вызов делается не больше `kProbeBudget` (1500)
проверок, а позиция обхода и лучший кандидат сохраняются и продолжаются со
следующего кадра. Раскладка находится за несколько кадров вместо одного
залипшего.

Чтобы продолжение не растянулось, `game_markers.cpp` при незавершённом обходе
(`layout_scan_in_progress()`) повторяет попытку на следующем кадре, а не через
свой обычный интервал в 60 кадров.

## 3. Ворота записи в кучу: снимок карты вместо разбора на каждую запись

`jni/src/game_viewmodel.cpp`, `jni/src/object_data_memory.h` (сделано раньше,
здесь для полноты)

`write_heap` читал и разбирал всю `/proc/<pid>/maps` перед каждой записью —
сотни килобайт и ~2 мс на одно поле, а быстрая стрельба с перезарядкой пишут
до семи полей в кадре. Теперь подтверждённый диапазон и текст карты кэшируются
на 0.25 с, разбор идёт без выделений памяти, а неподтверждённый адрес
по-прежнему проверяется по свежесчитанной карте.

## Что осталось как было

- Порционный скан реестра маркеров уже был ограничен временем
  (`kMarkerScanBudgetSec = 6 мс`) — не трогали.
- Пакеты тач-инъекции уже пропускают повторы и ждут на мьютексе, а не в
  активном цикле — не трогали.
- Поиск смещения позиции игрока, раскладки скелета, смещения имени
  `GameObject` — порядок кандидатов и правила отбора не изменены.

## Проверка

```sh
sh tools/memio/run.sh        # кэш блоков: перемежающийся обход
sh tools/esp/run.sh          # контракты источника: бюджет и возобновление обхода
sh tools/hostcheck/run.sh    # сборка и линковка всех исходников
```
