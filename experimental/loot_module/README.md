# Экспериментальный внутрипроцессный подбор

**Это прототип, не готовая функция обычного оверлея.** Основной `xvcen`
остаётся внешним executable; этот модуль не включён в его сборку и не загружается
автоматически. Нет готового загрузчика, поиска живого окна для загрузчика и
моста, вызывающего установку на безопасной точке Unity-потока. Android/сервер
не тестировались. Наличие API установки не означает готовую интеграцию.

## Что реализовано

- Отдельная опциональная ARM64 shared library `arena_loot_experimental`.
- Самостоятельный поиск живой кнопки: модуль сам находит в куче своего процесса
  единственный `UnityAction` со штатным callback и живой связью
  Button → InvokableCallList. Два кандидата — отказ, без угадывания. Скан читает
  не больше 512 МБ за вызов и продолжает с места остановки, поэтому один проход
  не занимает поток надолго. Фоновый поток (создаётся только явным вызовом arm)
  перепроверяет привязку и перепривязывается после пересоздания окна лута.
- Ядро `batch.h`: один синхронный проход в обработчике штатной кнопки, максимум
  256 слотов. Нет `await`, таймера, покадровой очереди или дополнительной кнопки.
- Адаптер `module.cpp`: чтение контекста текущего LootScreenViewImpl, локального
  PlayerManager/PlayerInventory, InventoryController, источника и cancellation
  token; обычные проверки наличия предмета/вместимости и обычный клиентский
  запрос `PlayerInventory.FYj` (release) / соответствующий метод beta.
- Повторная проверка контекста и идентичности holder/item/index. Остановка при
  закрытии/смене источника, отмене, занятом штатном контроллере, ошибке чтения,
  некорректном размере/индексе. Защита от reentrancy и повторного callback в кадре.
- Сначала проверяются все индексы, затем запросы идут от последнего к первому.
  Серверные обработчики напрямую не вызываются, инвентарь не подделывается.
- Счётчики `attempted` и `returned` различаются: исключение может произойти уже
  после постановки запроса. **Ни один из них не является числом полученных
  предметов или подтверждением сервера.** После частичного прохода нет повторов
  и возврата к штатной корутине. При исходном NotReady без запросов допустим
  штатный медленный обработчик.

## Что именно меняется

По цепочке `view.collectButton → onClick → m_Calls.runtimeCalls → InvokableCall`
ищется ровно один bound-instance `UnityAction` с target=этот view и известным
исходным callback. Multicast/неоднозначность/неизвестная форма отвергаются.

Единственная запись модуля в чужие объекты — CAS восьмибайтового
`UnityAction.invoke_impl` (+0x18) на собственный callback. Перед ней повторно
читается `/proc/self/maps`; принимается только разрешённая приватная RW-куча
через общий `object_data::heap_writable`. Target, MethodInfo и method_code
не переписываются. Остальные слушатели кнопки не удаляются. Собственная ARM64
точка входа содержит `bti jc`, поскольку invoker использует `BR x2`; затем
обычный прямой переход в диспетчер модуля. Это код новой DSO, не патч игры.

**Нет записи в код или данные libil2cpp/libunity либо другой существующей
библиотеки, нет mprotect, inline/PLT/vtable-hook, изменения scheduler или
продолжения корутины.** Вызовы обычного игрового кода могут, как и штатно,
инициализировать его метаданные и изменять состояние игры — это не патч модуля.
Это не «без записи памяти»: указатель в объекте игры всё-таки изменяется.
Остальные функции основного приложения, например существующий FPS-контроллер,
не входят в это утверждение о модуле.

Сборка определяется по build-id и оригинальным начальным инструкциям используемых
методов. Историческая точка патча задержки также проверяется **только чтением**.
При обнаружении старого патча установка отклоняется. Старый инструмент нужно
остановить, игру полностью перезапустить; скрытого восстановления библиотек нет.

## API и обязательства будущего хоста

Объявления: `api.h`. В API передаются реальные адреса текущего процесса:

- `arena_loot_probe_v1(base, view)` — только чтение/поиск кандидата. READY здесь
  не доказывает готовность всего контекста, правильность установки на устройстве
  или безопасность последующих нативных вызовов.
- `arena_loot_install_v1(base, view)` — требует Android ARM64 и поток с именем
  `UnityMain`. Вызывать **из нормального безопасного UI callback этого потока**,
  не из произвольно прерванного потока через регистры/ptrace. Имя потока — лишь
  дополнительный фильтр, не доказательство безопасной точки исполнения.
- `arena_loot_disable_v1()` — на том же потоке, вне активного batch. Отключает
  ускорение; восстановление CAS выполняется только для всё ещё достижимого из
  живой кнопки делегата с ожидаемой идентичностью. При исчезнувшем UI по старому
  адресу ничего не записывается. При ошибке восстановления модуль остаётся
  загруженным и передаёт последующие вызовы штатному callback.
- `arena_loot_report_v1(out, sizeof(*out))` — локальная диагностика, не IPC и не
  подтверждение доставки предметов.
- `arena_loot_arm_v2(base_hint)` — не вызывает игровой код: только чтения и один
  CAS указателя делегата. Поэтому её можно звать из любого потока сразу после
  загрузки модуля: ни живой управляемой ссылки, ни остановки чужого потока не
  требуется. Поток Unity модуль определяет сам — на первом настоящем нажатии
  кнопки. `base_hint` можно передать 0, тогда адрес образа ищется через
  `/proc/self/maps`. Возвращает READY, NOT_READY (взведён, окно лута ещё не
  открыто) или UNSUPPORTED.
- `arena_loot_restore_v2()` — так же потоконезависимо снимает привязку и
  останавливает фоновый поток. v1-функции оставлены для хоста, который уже
  держит живой view и сам работает на Unity-потоке.
- Переменная окружения `ARENA_LOOT_AUTOSTART=1` (вариант для LD_PRELOAD/wrap):
  взводит модуль сразу при загрузке. Без неё загрузка DSO не делает ничего —
  ни потоков, ни сканов, ни записей.

Новый view после пересоздания UI требует новой привязки. Загрузчик обязан иметь
живую управляемую ссылку во время установки, не вызывать игровые методы из
рабочего потока и оставлять DSO загруженной до завершения процесса. Линковка
использует `-z nodelete`, но **нельзя рассчитывать только на поддержку этого флага
конкретным Android linker**: копия делегата может пережить disable.

Установка намеренно не инициализирует чужие metadata slots вручную. Если
нужный MethodInfo/контейнер ещё не готов, возвращается NotReady; штатное
открытие/использование окна может потребоваться сначала. Tagged/MTE-указатели
в этом прототипе не поддерживаются и отклоняются, а не обнуляются перед вызовом.
Доступность `/proc/self/mem`/maps в домене игры также требует проверки.

## Проверки и сборка

```sh
# Без Android, без игры: ядро -O0/-O3, host .so, API и границы записи
sh tools/loot_module/run.sh

# Опциональная проверка ABI на исходных ARM64 ELF, требует Python Unicorn
python3 tools/loot_module/check_native.py /path/release/libil2cpp.so /path/beta/libil2cpp.so

# Явная отдельная сборка, требуется Android NDK; не загружает модуль в игру
ANDROID_NDK_HOME=/path/to/ndk sh tools/loot_module/build_android.sh
```

Android-артефакты складываются в игнорируемый `.tools/loot_module/`; игровые
бинарники в репозиторий не добавляются. Обычный `build.sh` модуль не собирает.

Host-тесты проверяют поиск точного делегата на синтетических объектах в своём
процессе, отказ для multicast/дубликатов/отсоединённого listener, реальный
heap CAS/restore, запрет RO и file-backed записей, а также синхронность/границы, отрицательные и повторные индексы,
отмену и смену идентичностей, изменившуюся вместимость, исключения после отправки,
снятие busy и reentrancy. Дополнительный Unicorn-тест исполняет оригинальные
`InvokableCall.Invoke` и callback вида `view.Action90`: проверяет аргументы
`(target, MethodInfo)`, переключение heap `invoke_impl` и восстановление для
release/beta. `AllowInvoke` в нём подменён тестовой заглушкой true; native endpoints
тоже тестовые. Никаких реальных предметов этот тест не переносит.

Отдельно проверяется сам поиск по куче на синтетических объектах в anonymous
RW-отображении: находится ровно один живой делегат, при двух живых привязках
скан отказывает, а уже установленный указатель кандидатом не считается. Тот же
тест проходит с `-fsanitize=address,undefined`.

## Нерешённые части

1. Доставка самого DSO в процесс игры: LD_PRELOAD/`wrap.<пакет>` или
   dlopen-инъекция из внешнего процесса. Модуль inert — сам он не подключается
   и никуда не стучится, но живая управляемая ссылка снаружи ему больше не
   нужна: окно лута он находит сам, держит привязку и восстанавливает её после
   пересоздания окна.
2. Реальная проверка путей runtime listener / presenter / singleton, жизненного
   цикла и GC, Android ABI/BTI, отключения/повторной установки. Оба layout —
   исследовательские, не объявлены поддержанными на устройстве.
3. Полное соответствие вспомогательным событиям штатной корутины
   (tutorial/guide/telemetry, состояния кнопок) пока не подтверждено.
4. Приём нескольких штатных запросов подряд сервером, ограничения частоты,
   изменение вместимости после ответа и момент обновления UI не проверены.

Проход без ожиданий убирает клиентскую паузу **только если адаптер удаётся
установить и контекст допускает весь проход**. Это не гарантия, что сервер
переместит всё в один момент. Исключения C++ перехватываются, но от SIGSEGV,
неверного ABI и всех гонок чтение/проверки не защищают. Модуль изменяет поведение
клиента и не обеспечивает защиты от бана.
