# tools/offsets — переопределение оффсетов после апдейта игры

Полный отчёт по конкретным константам — в `OFFSETS_UPDATE.md` (раздел 5 —
процедура, раздел 7 — что менялось в каждом апдейте). Откуда берётся каждый
оффсет, чем подтверждён и как его найти заново — в `PROVENANCE.md`.

## Обычный путь: одна команда

```bash
python3 tools/offsets/update_offsets.py            # что изменилось
python3 tools/offsets/update_offsets.py --apply    # и записать в заголовок
```

Скрипт сам распаковывает новые дампы из рабочего дерева и старые из коммита,
где лежали предыдущие, сверяет каждую константу заголовка с полем, за которое
она отвечает, и печатает таблицу «было → стало». Затем — сборка и строчка в
`OFFSETS_UPDATE.md`.

Порядок важен: **сначала залить новые дампы, потом запускать**, пока заголовок
ещё описывает прошлый билд. Если подсунуть дамп через поколение, смещения в
карте будут указывать на чужие поля; скрипт это замечает (сравнивает читаемые
имена полей) и отказывается работать, вместо того чтобы выдумать изменения.

Отдельно есть проверка без прошлого билда:

```bash
python3 tools/offsets/update_offsets.py --verify   # сверить заголовок с текущим дампом
```

Она опознаёт поля по читаемым именам (`lastSavedPosition`, `m_Name`) и потому
проверяет не всё, зато её можно запускать когда угодно. Именно так нашлась
многолетняя ошибка в `PLAYER_POSITION` (0x1D0 вместо 0x1D4).

Соответствие «константа → поле структуры» лежит в `offsets_map.json`; при
`--apply` скрипт обновляет и его (смещение, новое имя поля после
переобфускации — для ВСЕХ полей, а не только изменившихся, иначе карта
описывает прошлый билд и следующий прогон пойдёт по чужим смещениям).
Константы с `"kind": "runtime"` — раскладка Unity/IL2CPP и камера из libunity:
из `dump.cs` они не выводятся и проверке не подлежат.

**`--apply` можно запускать ровно один раз на дамп.** После него карта описывает
новый билд, и повторный прогон сдвинет значения ещё раз (реальный случай:
`PLAYERWEAPON_PIECE` 0x100→0x110→0x120). Скрипт это ловит и останавливается
(«карта уже описывает НОВЫЙ дамп»); если заголовок всё же испорчен —
`git checkout -- jni/src/game_offsets.h tools/offsets/offsets_map.json` и один
прогон заново.

Поле в новом дампе ищется сначала по имени (читаемые имена вроде
`lastSavedPosition` переживают апдейт), а если имя обфусцировано — позиционным
выравниванием списка полей по последовательности типов.

RVA скрипт подбирает **по отпечатку со старого дампа**, а не «верхним
кандидатом»: находит в старом дампе кандидата, равного текущему значению
заголовка, запоминает его отпечаток (число обращений + прочитанные статик-поля)
и в новом берёт кандидата с тем же отпечатком. Без этого `GameControllerBase`
получает чужой слот (в билде `62a8534`: 0xD8E4CD8 вместо верного 0xD8D61E8) —
и ESP молча пустой. Прогоны идут с `--methods 3000`: на 400 методах у
`PlayerManager` кандидатов не находится вовсе. Если отпечаток не совпал, скрипт
пишет предупреждение — тогда решать руками.

Что скрипт **не** делает: не угадывает переименованный класс, которого не стало
в новом дампе (скажет об этом и отправит к `il2cpp_layout.py find`), и не
трогает константы, которых нет в карте — а они есть: окно скана
`TOD_SCAN_RVA_BEGIN/END` (время суток) уезжает каждый билд вместе с RVA.
Полный список того, что остаётся руками, — в `OFFSETS_UPDATE.md` §5.1 и в
`PROVENANCE.md` §F.

## Ручной путь: если что-то не сошлось

```bash
# 1. распаковать новые дампы (из рабочего дерева) и старые (из коммита до аплоада)
tools/offsets/extract_dumps.sh /tmp/new
tools/offsets/extract_dumps.sh /tmp/old <коммит-с-прошлыми-дампами>

# 2. какие структуры вообще поменяли раскладку
python3 tools/offsets/il2cpp_layout.py --old /tmp/old/il2cpp.h --new /tmp/new/il2cpp.h diff

# 3. по каждой изменившейся — полный список полей и ручное сопоставление
python3 tools/offsets/il2cpp_layout.py --old /tmp/old/il2cpp.h --new /tmp/new/il2cpp.h \
        show Oxide_LootObject_Fields

# 4. RVA глобальных TypeInfo (меняются ВСЕГДА)
python3 tools/offsets/typeinfo_rva.py --so /tmp/new/libil2cpp.so --script /tmp/new/script.json \
        Oxide.PlayerManager Oxide.GameControllerBase Mirror.NetworkClient
# контроль: та же команда на /tmp/old должна выдать значения, которые сейчас в git
```

## Почему именно так

* **Имена классов и полей переобфусцируются каждый билд** (`fvp`→`pmi`,
  `wK`→`ij`, `Mo`→`sR`). Diff по именам покажет «ничего не изменилось» и
  проглотит все переименованные поля. `il2cpp_layout.py diff` сравнивает
  **позиционно**: последовательность (смещение → тип), обфусцированные типы
  нормализуются в `OBF_o`.
* **Переименованный класс ищется по форме**, а не по имени:
  `il2cpp_layout.py find --new /tmp/new/il2cpp.h "WeaponBase_o*" "Oxide_WeaponPiece_o" "UnityEngine_Transform_o*"`
  — так был найден `sR_Fields` вместо старого `Mo_Fields`. Аргументы —
  обычные подстроки, не регэкспы.
* **`dump.cs` этого дампера не содержит смещений полей** — только значения
  enum'ов (`public static literal ... = 13;`). Смещения живут в `il2cpp.h`
  в комментариях `/* 0xNN */`.
* **`ScriptMetadata` в `script.json` пустой**, поэтому RVA типов берутся
  дизассемблированием: `adrp/ldr` → addend релокации `R_AARCH64_RELATIVE` →
  слот в `.data`; оставляем только те, что затем разыменовываются как
  `ldr x8,[klass,#0xB8]` (`Il2CppClass::static_fields`) — ровно так к ним
  ходит `game.cpp`.
* `libil2cpp.7z` сжат LZMA2 + ARM64 BCJ; `py7zr` такой фильтр не умеет,
  поэтому `extract_dumps.sh` вынимает упакованный поток и гонит его через
  `xz --format=raw --arm64`.

## Файлы

| файл | что делает |
|---|---|
| `update_offsets.py` | всё вместе: распаковка, сверка, отчёт, `--apply` |
| `offsets_map.json` | константа → структура и поле, обновляется автоматически |
| `PROVENANCE.md` | откуда берётся КАЖДЫЙ оффсет и как его найти заново (имена классов, якоря, ловушки билда) |
| `make_provenance.py` | пересобрать `PROVENANCE.md` из карты и заголовка |
| `extract_dumps.sh` | распаковка `dump.7z` и `libil2cpp.7z` (в т.ч. из старого коммита) |
| `il2cpp_layout.py` | позиционный diff структур, `show`, поиск класса по форме |
| `typeinfo_rva.py` | RVA глобальных TypeInfo дизассемблированием |

Зависимости: `py7zr` и `capstone` (`pip install py7zr capstone --break-system-packages`),
`xz` из состава xz-utils.
