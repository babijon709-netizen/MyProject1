# Диагностический журнал (diag.log)

Зачем: «у одного из пользователей не работает ни одна функция, но меню
запускается». Весь софт стоит на одной цепочке, и отказ любого её звена снаружи
выглядит одинаково — меню живо, функций нет:

```
найти процесс игры -> открыть /proc/<pid>/maps -> найти base libil2cpp.so
   -> пробно прочитать память (process_vm_readv) -> найти классы по RVA
   -> собрать кадр (камера + локальный игрок + реестр игроков)
```

Журнал проходит эту цепочку шаг за шагом и пишет, где именно она порвалась
именно у этого человека. Журнал всегда включён, отдельно ничего активировать
не нужно.

## Где лежит и как получить

* файл: `Download/diag.log` на телефоне («Загрузки» — полный путь
  `/storage/emulated/0/Download/diag.log`), чтобы его можно было найти и
  переслать из любой файломенялки;
* если запись в «Загрузки» на устройстве не прошла — журнал ляжет рядом с
  конфигами: `/storage/emulated/0/benzhack/diag.log` (выбор места печатается
  в шапке журнала строкой `файл журнала: ...`);
* зеркало каждой строки в logcat, тег `xvcen.diag`: `adb logcat -s xvcen.diag`.

Пользователю достаточно написать: *«запусти софт и игру, включи функции,
поиграй минуту и пришли файл `diag.log` из Загрузок»*. Переполненный
файл (400 КБ) переезжает в `diag.log.old` — если прислали оба, смотреть оба
(старый — начало сеанса).

Формат строки: `[секунды от старта] текст`. В покое журнал молчит, так что
каждая строка — событие.

## Как читать: типовые картины

Строки идут в порядке цепочки привязки. Диагноз — по ПЕРВОЙ строке, которая
сообщает об отказе; всё после неё — следствие.

| Что в журнале | Причина | Что сказать пользователю |
| --- | --- | --- |
| `attach: процесс игры НЕ НАЙДЕН (искал [...] и [...])` повторяется | игра не запущена, либо установлена под другим пакетом (клон/другой магазин) | запустить игру до софта; сказать, какой у него пакет |
| `attach: /proc/N/maps НЕ ОТКРЫЛСЯ errno=...` | чужие `/proc` не читаются: урезанные права, не тот способ запуска | проблема окружения: софт должен быть запущен так же, как у работающих пользователей |
| `attach: libil2cpp.so ... ПОКА НЕ НАЙДЕНА` пару раз, потом привязка | норма: игра ещё грузится | ничего |
| `attach: ... ПОКА НЕ НАЙДЕНА` повторяется всё время | игра не та сборка (32-битная/мод) или стоит не туда, куда ищем | уточнить, откуда игра |
| `attach: pid=N base=0x...: ПРОБНОЕ ЧТЕНИЕ ПАМЯТИ НЕ ПРОШЛО errno=EPERM` | **чужую память читать не дают вообще** (SELinux/права ядра). Меню при этом живо | окружение: так не заработает ни одна функция. Сравнить с устройством работающего пользователя (версия Android, root, запуск) |
| `attach: ... ELF: 32 бит` или `x86` + `ВНИМАНИЕ: игра НЕ 64-битная arm64` | у пользователя 32-битная сборка игры или эмулятор | поставить arm64-клиент игры |
| `PlayerManager: по RVA 0x... читается класс '...'/'...', ожидался 'Oxide'/'PlayerManager'` | **версия игры не та, под которую собраны оффсеты** (обновление, бета вместо релиза, репак) | проверить выбор версии в меню; если и релиз свежий — игре нужен новый дамп |
| `PlayerManager: слот типинфо по RVA 0x... ПУСТ (0)` | то же, но класс вообще не нашёлся | то же |
| `PlayerManager: static_fields=0 ...` надолго | статика класса не создана (игра не дошла до меню) или раскладка il2cpp другая | дождаться полной загрузки игры; если не оживает — новый дамп |
| `память игры за 10 с: чтений 0 ок / N сбоев (EPERM ...)` | чтения целиком запрещены — привязка «ок», а памяти не видно | то же, что EPERM выше |
| `память игры за 10 с: чтений N ок / M сбоев (EFAULT ...)` и классы ок | норма: одиночные EFAULT — это пробы опциональных объектов | ничего |
| `запись памяти: ПЕРВЫЙ СБОЙ ... EPERM` | читать дают, писать нет: x-ray и «всегда день» молча не работают | отдельно про запись — окружение |
| `тач: ... НЕ НАЙДЕН / /dev/uinput НЕ ОТКРЫЛСЯ / UI_DEV_CREATE НЕ ПРОШЁЛ` | тач-инъекция не поднялась: аим и автофарм не смогут водить пальцем, остальное — может работать | окружение: uinput/grab запрещён; сравнить с работающими устройствами |
| `ESP: 240 кадров подряд без камеры/локала — сбрасываю кеши` | кадр долго не собирается; причина — в строках PlayerManager/GameController выше | смотри классы выше |
| `ESP: кадр собран (камера+локал ок ...)` | цепочка цела, чтение памяти и оффсеты в порядке — дальше функции работают | если «не работает» при этой строке — проблема не в привязке, смотреть конкретную функцию |
| `автофарм: причина простоя -> N (...)` | текущая причина простоя фарма (2 — нет привязки, 5 — нет камеры, 6 — не тот инструмент и т.д.) | по подписи |

Полезно держать в голове «здоровый» лог от работающего пользователя для
сравнения: запуск → `версия клиента` → `attach: найден процесс` →
`ELF: 64 бит, aarch64` → `PlayerManager: класс ок` → `локальный игрок: ок` →
`ESP: кадр собран` → `тач: инъекция поднята`, дальше только редкие
`память игры за 10 с: чтений N ок`.

## Что пишется и где в коде

Всё в одном модуле `jni/include/diag.h` (заголовочный, без .cpp):

* выбор места файла: «Загрузки», при отказе записи — каталог конфигов
  (`diag::init(dir, fallback)`);
* шапка окружения при запуске: модель/версия Android/ABI, SELinux,
  yama/ptrace_scope, uid, штамп сборки бинарника;
* цепочка привязки: `main.cpp` (поток привязки), `game.cpp`
  (`get_base`, `esp_init` — пробное чтение + класс/разрядность ELF + путь APK);
* резолв классов и реестра игроков: `game.cpp`
  (`resolve_runtime_player_list`, `resolve_local_player`) — с печатью того,
  что реально прочиталось по RVA вместо ожидаемого класса;
* здоровье конвейера: `esp_get_boxes` (сброс по вотчдогу, первый собранный
  кадр), `esp_farm_debug` (причины простоя фарма), `always_day_tick` (TOD);
* счётчики `process_vm_readv/writev` по errno: гистограмма в срезе
  `память игры за 10 с` (пишется из потока привязки);
* тач-инъекция: `Android_touch/TouchHelperA.cpp` и повторные попытки в
  `main.cpp`.

Правила, чтобы журнал оставался читаемым:

* повторяющиеся сообщения печатаются не чаще своего интервала (`diag::due`);
* статусы резолва классов печатаются при смене, негатив — не чаще раза в 30 с;
* строки журнала — только по-русски и НЕ переводятся (как служебный лог
  автофарма); поэтому вызовы `diag::logf` вырезаются сборщиком таблиц
  перевода (`tools/lang/gen_tables.py: remove_diag_logf`), а строковые
  константы для журнала (`farm_reason_text`, `elf_arch`) живут в `diag.h`,
  а не в `game.cpp`;
* у «работающего» пользователя журнал почти пуст — это нормально.
